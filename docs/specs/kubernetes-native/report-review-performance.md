# Review report — Performance

- Scope: uncommitted changes (mosquitto submodule `src/otel_metrics.c/.h`, `src/sys_tree.c/.h`, `src/mosquitto.c`, `src/conf.c`) — performance of the OTLP metrics exporter and its impact on the broker hot path
- Method: `/Users/michal/.agents/skills/review/references/review-bottleneck/instructions.md` (static analysis first, conservative ranges, impact/effort → P0–P3), read-only
- Evidence base: full read of `mosquitto/src/otel_metrics.c` and `mosquitto/src/sys_tree.c`; `src/loop.c:188,204-206`; `src/mosquitto.c:457,558-566`; generated code for the atomic operations via `clang -S` on this machine (arm64) and `clang -target x86_64-apple-macos11 -S`; `test/otel/zero-overhead.sh`; `test/broker/24-otel-otlp-metrics.py`. No profiler/benchmark run.

## Verdict

The exporter is correctly off the broker's critical path: all metric reads, JSON encoding and libcurl I/O run on the dedicated `otel__thread_main` thread, so steady-state effect on MQTT throughput is limited to two atomic primitives that `WITH_OTEL` adds to hot paths — a sequentially-consistent store per event-loop iteration (P1, avoidable) and a locked read-modify-write per counter update (P2, bounded). The one real latency risk is shutdown, which is bounded by `otlp_timeout` (P4).

## Event-loop impact (explicitly answered)

- **Blocking curl on the export thread only — confirmed.** `otel__export_once` (snapshot, encode, `otel__post`) is called solely from `otel__thread_main` (`otel_metrics.c:630`); the event loop never touches curl. `loop.c:204-206` only calls `sys_tree__update`, which now contains the P1 store. Covered end-to-end by `test_non_blocking` (G-C2.3) in `test/broker/24-otel-otlp-metrics.py`.
- **Cost added to the event loop when `WITH_OTEL=ON`:** exactly two items — one seq_cst atomic store per `mosquitto_main_loop` iteration (P1) and one seq_cst atomic RMW per counter update on the packet paths (P2). Both are unconditional under the flag; the `zero-overhead.sh` harness covers only the OFF build, so there is no measured OFF-vs-ON hot-path delta.
- **Reader side:** the export thread performs ~50 atomic loads plus 27 `_Atomic double` loads per export; the per-metric reads are independent (no snapshot consistency), which is documented and accepted (`sys_tree.h:145-149`).
- **Not quantified here (needs a run):** packets/s at which the P1/P2 barriers become visible; recommended tooling = `perf stat -e instructions,cycles,bus-cycles` or `perf record` on the broker with OFF vs ON, plus the existing `zero-overhead.sh` extended to a throughput A/B. Static analysis cannot produce a throughput number.

## Good practices / strengths

- All I/O and encoding is off the broker thread; `CURLOPT_NOSIGNAL=1` avoids signal-handler interference in the multi-threaded broker.
- `samples` is sized once from the compile-time maxima (`otel_metrics.c:569`), so the snapshot loop needs no growth/`realloc`.
- The snapshot is O(metrics) (~52 + 27) with no scans over clients/subscriptions, i.e. independent of broker state size — good scaling property.
- The `_Atomic` conversion is compile-flag-scoped (`sys_tree.h:118-128`, `sys_tree.c:40-47`), so the non-OTEL hot path is byte-identical; `test/otel/zero-overhead.sh` gates symbol/dependency containment.
- Export interval is configurable (`otlp_export_interval`) and validated `>= 1` (`conf.c:2352-2357`), so an operator can trade overhead for resolution.
